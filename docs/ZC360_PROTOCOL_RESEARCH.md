# Jonsbo ZC-360 USB Protocol / Transport Research

## Hardware

USB ID:

    43a8:0e61

Product descriptor:

    TURZX-338inch-r

The ZC-360 contains three independent USB display controllers.

Native framebuffer:

    180 x 640

Pixel format:

    BGR888

Logical content orientation used by the driver:

    640 x 180

The logical image is rotated clockwise into the controller's native
180x640 portrait framebuffer before transmission.

---

## Frame protocol

A raw framebuffer contains:

    180 * 640 * 3 = 345600 bytes

Each framebuffer protocol record contains:

    32-byte header
    480-byte pixel payload

Total:

    512 bytes / record

There are exactly:

    345600 / 480 = 720 records

per framebuffer.

The vendor Windows application groups eight records into each USB bulk OUT:

    8 * 512 = 4096 bytes

Therefore one complete framebuffer consists of:

    90 * 4096-byte USB bulk OUT transfers

per panel.

Sequence numbers are:

    1 ... 720

The first USB transfer contains records 1-8.
The last USB transfer contains records 713-720.

All 720 32-byte framebuffer headers generated by the Linux driver were
compared against a captured Windows frame and matched byte-for-byte.

---

## Commands

Command packets are 32 bytes and use:

    AA 55

as their leading magic.

Command payload bytes 2:10 are DES-ECB encrypted.

Observed commands include:

    56  controller initialization
    84  brightness
    86  rotation
    88  first-frame/live-mode commit

---

## First-frame controller state

Freshly powered controllers behave differently from steady state.

Known-good Linux/PyUSB startup captures showed, on all three displays:

1. Commands 56, 84 and 86 are sent.
2. The first COMPLETE framebuffer is accepted unusually quickly:
   approximately 10.4-10.6 ms for all 90 transfers.
3. The following status response is:

       0x60

4. Command 88 is sent.
5. Its response is:

       0x59

6. After the commit/settle transition, normal framebuffer transfers take
   approximately 37.5 ms per individual panel.
7. Steady-state frame status becomes:

       0x62

This strongly indicates that command 88 transitions the controller from its
initial/boot framebuffer state into normal live-display operation.

---

## Official Windows three-panel scheduling

USBPcap captures of the official Jonsbo Windows application show that the
three displays are NOT updated as three complete frames serially.

Instead, the application maintains approximately one outstanding 4096-byte
bulk OUT transfer per physical panel.

Each panel behaves like:

    submit 4096-byte chunk
    wait for completion
    immediately submit next chunk

The three independent streams are interleaved by the host/controller.

All three streams must reach the same frame boundary.

Observed steady-state frame boundary:

    all 90 OUT transfers complete on all 3 panels
                  |
                  v
          ~12.7 ms quiet period
                  |
                  v
       3 status IN transfers submitted
          essentially simultaneously
                  |
                  v
         wait for all 3 responses
                  |
                  v
             next frame

The official Windows application therefore achieves approximately 16 FPS
across all three displays.

## Linux asynchronous reproduction

A prototype using python-libusb1/libusb asynchronous USB transfers was tested.

Configuration:

    one asynchronous OUT transfer object per physical panel
    one outstanding 4096-byte transfer per panel
    completion callback immediately rearms that panel's next chunk
    common frame barrier after all 90 chunks
    ~12.7 ms frame/status delay
    three asynchronous status IN requests submitted before processing events

Measured result:

    framebuffer write phase: 46.578 ms
    first-submit span:        1.134 ms
    frame/status gap:         12.832 ms
    status phase:             0.123 ms
    status-submit span:       0.018 ms
    complete transaction:     59.539 ms
    equivalent frame rate:    16.80 FPS
    statuses:                 0x62 / 0x62 / 0x62

The previous framebuffer contained solid red, green and blue test images.

After one asynchronous gray triplet, all three displays appeared completely
gray with no visible stale RGB regions or remnants of the built-in Jonsbo
logo.

This is therefore the current preferred implementation model for
three-panel steady-state updates.

## IMPORTANT: USB ownership / controller-state warning

Repeatedly releasing and reclaiming these displays within the same physical
power session has produced unreliable controller state.

Observed failure mode:

    built-in Jonsbo logo remains partially visible
    while only portions of new framebuffer content are displayed

Subsequent otherwise-valid framebuffer writes may not fully recover the
display.

A full physical power cycle restores normal operation.

Therefore applications SHOULD:

    claim all three interfaces once
    initialize all three
    retain ownership for the lifetime of the process/session
    avoid unnecessary release/reclaim cycles

Renderer or UI processes should communicate with a persistent USB-owning
daemon rather than independently claiming the devices.

Do not assume that a retained factory-logo region means the framebuffer
packet format is incorrect. It can instead indicate a poisoned controller
state caused by USB ownership cycling.

---

## Blocking PyUSB concurrency warning

A test implementation used three Python threads, each issuing synchronous
blocking PyUSB writes to one display.

usbmon superficially resembled the Windows interleaving pattern and achieved
higher throughput than fully serial operation.

However, this implementation produced persistent stale-frame regions and
should NOT be used as the production three-panel transport.

True asynchronous libusb transfers are the currently validated approach.

---

## Capture notes

Linux usbmon captures may lose records when capturing this traffic.

For transfer size, `usb.urb_len` should be used. In truncated captures,
`usb.data_len` may not represent the complete 4096-byte submission.

Important captures from the reverse-engineering session included:

    zc360-windows-1.pcap
        official Windows Jonsbo application

    zc360-pyusb-good-init.pcap
        known-good Linux PyUSB startup / first-frame transition

    zc360-async-clean.pcap
        successful python-libusb1 asynchronous prototype

Capture loss means absence of an individual packet in usbmon should not be
treated as proof that libusb failed to submit or complete the transfer when
the application itself reports successful completion.

---

## Production direction

The intended production architecture is:

    persistent daemon
        |
        +-- claim all 3 devices once
        +-- initialize all 3
        +-- perform first-frame / command-88 transition safely
        +-- retain USB ownership
        +-- asynchronous libusb steady-state transport
        |
        +-- Unix socket
              |
              +-- renderer / UI clients

The renderer must never directly own the USB interfaces.
